# กฎการทำงาน — Bridge Declarer Trainer

โปรเจกต์ทำครบ M1–M13 แล้ว (ดู `TASKS.md`) งานทุกชิ้นหลังจากนี้ ไม่ว่าจะเป็นฟีเจอร์ใหม่ แก้บั๊ก หรือปรับเล็กน้อย
ให้ทำ**แบบเดียวกับตอนจบ milestone** และ**ต้องลง task ทุกครั้ง** เพื่อให้ตรวจย้อนหลังได้ว่าทำอะไร เพราะอะไร
และตรวจอะไรไปแล้วบ้าง

เอกสารหลัก: `SPEC.md` (สเปก — ต้องตรงกับของจริงเสมอ), `TASKS.md` (task + สถานะ), `DECISIONS.md` (การตัดสินใจ — ใหม่สุดอยู่ล่าง)

## 1. ทุกงานคือ milestone หนึ่งตัว

- งานหนึ่งเรื่องที่ผู้ใช้ขอ = milestone ใหม่หนึ่งตัว เลขต่อจากตัวล่าสุดใน `TASKS.md` (`M14`, `M15`, …)
  งานเล็กหลายชิ้นที่เกี่ยวกันและทำใน branch เดียวกันรวมเป็น milestone เดียวได้
- ถ้าระหว่างทำผู้ใช้ขอเพิ่ม/เปลี่ยน ให้เพิ่มเป็นข้อย่อยใน milestone เดิม (หรือเปิด milestone ใหม่ถ้าเป็นคนละเรื่อง)
  แล้วจดในสถานะว่าผู้ใช้เปลี่ยนอะไร เมื่อไหร่

## 2. เริ่มงาน (ใช้ skill `/start-task`)

1. แตก branch จาก `main` ก่อนแก้อะไร: `feature/<slug>` (ฟีเจอร์), `fix/<slug>` (บั๊ก), `chore/<slug>` (อื่น ๆ)
2. **ลง task ใน `TASKS.md` ก่อนเขียนโค้ด**: หัวข้อ `## Mxx — <ชื่อ>`, บรรทัดที่มา (ใครขอ / ปัญหาอะไร / วันที่),
   ข้อย่อย `- [ ] **xx.1** …` และ `**เสร็จเมื่อ:** …` ที่ตรวจได้จริง (test อะไรต้องผ่าน, หน้าจอไหนต้องเห็นอะไร)
3. อ่าน `SPEC.md` ส่วนที่เกี่ยวข้อง และ `DECISIONS.md` ของ milestone ที่เคยแตะโค้ดส่วนเดียวกัน

## 3. ระหว่างทำ

- ติ๊ก `[x]` ทีละข้อเมื่อข้อนั้นผ่านจริง ไม่ติ๊กล่วงหน้า
- ตัดสินใจอะไรที่สเปกไม่ได้บอก หรือทำต่างจากสเปก → จดใน `DECISIONS.md` หัวข้อ `## Mxx — <ชื่อ> (YYYY-MM-DD)`
  เขียนเหตุผลด้วย ไม่ใช่แค่ผล (รวมทางที่ลองแล้วไม่ได้ผล)
- พฤติกรรมที่ผู้ใช้เห็นเปลี่ยน → แก้ `SPEC.md` ให้ตรง (เช่น ตั้งค่าใหม่ → §7.6, ปุ่ม/คีย์บอร์ด → §8)
- หน้าจอ ปุ่ม หรือเมนูเปลี่ยน → ตรวจบท 14 ของคู่มือ (`src/learn/chapters/ch14.ts`) ที่อธิบายปุ่มตามหน้าจอ
  ศัพท์อังกฤษใหม่บนหน้าจอต้องอยู่ในอภิธานศัพท์ (test ตรวจให้บางส่วน)
- พฤติกรรมใหม่ต้องมี test: unit test สำหรับ logic, e2e สำหรับสิ่งที่ผู้ใช้กด (รันทั้ง desktop และมือถือ)
- โค้ดเขียน comment เป็นภาษาอังกฤษ ข้อความบนหน้าจอและเอกสารเป็นภาษาไทย ตามของเดิม

## 4. ปิดงาน = ตรวจแบบจบ milestone (ใช้ skill `/finish-task`)

ปิดงานได้เมื่อครบทุกข้อ:

1. ข้อย่อยทุกข้อ `[x]` และเงื่อนไข "เสร็จเมื่อ" ผ่านจริง
2. check ทั้งหมดผ่าน: `pnpm format:check`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:e2e`
   (ถ้าแตะ `src/solver/` ให้รัน `pnpm bench` และจดผลด้วย) — ห้ามข้าม test ที่ fail หรือปิด test เพื่อให้ผ่าน
3. งาน UI: ดูภาพหน้าจอจริงทั้ง desktop และมือถือกว้าง 360 px — ไม่มี scroll แนวนอน ไม่มีอะไรบังกัน
   ไม่มี error ใน console
4. เขียนบันทึกสถานะท้าย milestone ใน `TASKS.md`:
   `> **สถานะ (YYYY-MM-DD):** …` — ทำอะไร ไฟล์หลัก test ที่เพิ่ม ผลตัวเลข (เช่น `pnpm test` 425 ข้อ, e2e 66 ข้อผ่าน)
   และ `> **ส่งต่อ:** …` ถ้ามีเรื่องค้าง ข้อจำกัด หรือสิ่งที่คนต่อไปต้องรู้
5. `DECISIONS.md` มีหัวข้อของ milestone นี้ (ถ้าไม่มีการตัดสินใจอะไรเลย ไม่ต้องสร้าง)
6. commit หนึ่งครั้งต่อ milestone บน branch ของงาน ข้อความแบบเดิม: `Mxx: <หัวข้อ> — <สรุปสั้น>`
   (ภาษาอังกฤษ เหมือน `M12: beginner guide + beginner mode — …`) แก้ตามหลังใน milestone เดียวกันใช้ `Mxx: fix …`
7. push / merge เข้า `main` / เปิด PR / deploy **เฉพาะเมื่อผู้ใช้สั่ง**
8. รายงานผู้ใช้เป็นภาษาไทย: ผลลัพธ์ก่อน แล้วตามด้วยสิ่งที่ตรวจ และเรื่องที่ต้องให้ผู้ใช้ตัดสินใจ

## 5. ตรวจย้อนหลัง

- ทุก commit หลัง M13 ต้องมีเลข milestone (`Mxx:`) จึงหา task / การตัดสินใจที่ตรงกันได้ด้วย `git log --grep "M14"`
  และค้น `M14` ใน `TASKS.md` / `DECISIONS.md`
- ห้ามลบหรือเขียนทับบันทึกสถานะเก่า ถ้าของเดิมผิดให้เพิ่มบันทึกใหม่ที่บอกว่าแก้อะไร

## หมายเหตุเครื่องมือ (Windows)

- รัน `pnpm` / `git` ผ่าน Bash (PowerShell ไม่มี pnpm ใน PATH)
- repo เป็น LF (`.gitattributes eol=lf`) — ระวังสคริปต์ที่เขียนไฟล์เป็น CRLF
- `pnpm test:e2e` build ใหม่และเปิด `vite preview` พอร์ต 4173 เองทุกครั้ง
